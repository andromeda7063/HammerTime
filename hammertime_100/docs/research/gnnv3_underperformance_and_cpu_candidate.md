# GNNv2 underperformance and GNNv3 CPU candidate

## Scope and evidence

The reported GNNv2 result is MAE 0.083 and R² 0.09. Until a run manifest identifies the exact checkpoint and metric partition, those are reported values rather than reproduced measurements. The current config `hammertime_100/configs/train_2023_fastf1_season_gnnv2.yaml` uses 20 node inputs, hidden width 64, four heads, three GATv2 layers, GraphNorm, 0.20 dropout, 0.15 edge dropout, residual connections, typed physical-v2 edge values, own-car bypass, causal gated dilated temporal blocks [1,2,4], future-speed auxiliary prediction, SmoothL1 beta 0.02, batch size 256, Adam learning rate 5e-4, weight decay 5e-4, 30 epochs, patience 10, and plateau scheduling. The same file sets 10-frame history, five-frame horizon, and two-frame stride. The exact run hash, effective config, score scope, best epoch, train curve and target baseline are not identified by this score alone.

`DeltaT_Sector` is measured in seconds. The target builder (`hammertime_100/src/target.py`) subtracts its clean-air mini-sector reference from future sector duration and applies the existing clip. The evaluator (`hammertime_100/src/evaluate.py`) computes R² as standard coefficient of determination and still reports the existing acceptance range. R² 0.09 means the model leaves 91% of the scored partition's centered sum-of-squares; it does not mean 9% accuracy. MAE 0.083 means 83 ms only if this is the evaluator's target in seconds and the score is over the intended held-out rows. First verify the artifact, exact scored partition and coverage.

The target reference is built from session observations before race-level splitting. Thus the experiment estimates a calibrated future residual under the current protocol. It does not establish a prospectively known clean-air reference for a wholly unseen weekend. Changing that estimand requires scientific review; this candidate preserves it.

## Diagnoses that the current score cannot distinguish

- **Underfit or optimization failure:** unknown without train/validation curves and a short train-only memorization diagnostic. SmoothL1 beta 0.02 focuses on the quadratic region only within 20 ms of residual and is linear beyond; with outliers, scale mismatch, or awkward gradient balance, a 30-epoch schedule might stop before useful fitting. The .05 auxiliary speed loss is normalized separately; compare actual primary and auxiliary gradient magnitudes before changing its weight. Do not assume that adding neurons fixes either problem.
- **Weak features or missing information:** the graph contains physical-v2 edge channels (RBF time-gap, gap metres, relative speed, position coverage, wake corridor), and circuit-context node features plus speed/history covariates. Edge data reach GAT attention coefficients and the typed path separately transforms node and edge values into messages. These encode a useful physical prior, but not all aerodynamics, tyre state, fuel, weather, or setup. The model cannot recover unobserved causal conditions. Compare a train-mean/train-median baseline, own-history-only model, and tree baseline on the exact same frozen split before concluding which information is absent.
- **Oversmoothing or overmixing:** three residual, normalized GATv2 layers are not proof of oversmoothing. Three hops may mix all nodes in a 20-node ring, but graph diameter and degree vary by frame. Measure pairwise node embedding similarity, per-layer feature variance, and train/validation behavior before introducing PairNorm or more layers. The new candidate skips attention/depth while preserving one edge-conditioned pass at each time.
- **Too much data / neuron count:** overlapping windows are correlated; larger nominal sample counts do not imply equivalent independent observations. Width 64 is moderate for 20 nodes and 20 inputs, so “too many neurons” is unsupported. Capacity should be diagnosed from train vs validation error, not parameter-count intuition. A batch of 256 on 16 GiB can consume avoidable transient memory; 128 is a conservative overnight candidate, not a known optimal batch.
- **Metrics/objective mismatch:** selection uses validation MAE while training uses SmoothL1 primary objective plus auxiliary speed loss. R² responds to squared residuals and residual variance; MAE responds linearly. SmoothL1 beta and score behavior warrant review, but changing objective on the same overnight run would confound an architecture/hyperparameter candidate. First collect train-online MAE and validation MAE; run a separate preregistered objective ablation only if warranted.
- **Leakage and statistical uncertainty:** target reference is calculated before split; windows overlap and adjacent car/time targets share context. Report exact race split, counts by race, effective-window overlap, and baseline scores. Do not tune on test metrics or use test-partition means as a deployable baseline.

## Why this GNNv3 candidate

The new opt-in `model.spatial_encoder: edge_temporal` uses the existing `_typed_messages` physical edge-conditioned operator directly after node projection on every input frame. It retains frame-level dynamic leader/follower edges and the complete temporal sequence. It then uses the existing causal gated temporal convolution, primary sector head, own-car residual head, active-node masks and optional future-speed head. It skips GAT/GATv2 attention and three spatial propagation passes, lowering CPU cost and reducing inter-frame node mixing. Physical edge values transform message content rather than only choosing attention weights. This is a hypothesis, not a claim that attention caused the low score or that the typed channels are sufficient.

The profile lowers dropout from .20 to .10 and edge dropout from .15 to 0 because physical rings can be sparse and the latter currently removes one in six physical edges stochastically. It retains 64 hidden channels and learning rate 5e-4, reduces weight decay to 1e-4, halves batch size to 128 for memory headroom, and uses a cap of 45 epochs with patience 12. These are limited, directional adjustments for one overnight attempt, not a search result. The profile keeps SmoothL1 beta, auxiliary weight, temporal receptive field, preprocessing, target, split, and evaluation unchanged.

Runner accepts only a narrow `model`/`train` overlay after exact cohort validation. This is essential because preparation fingerprints include the full config: applying a model-only profile before the cache lookup would change the cohort key and could trigger the two-hour data build again. `--require-existing-caches` fails if any raw/normalized race cache or prepared cohort does not match. Keep the original output directory and base config identity for lookup; the model/training fingerprint produces a distinct checkpoint folder. Do not force a rebuild by removing the fail-fast option.

## Interpreting one run

Log train-mode online MAE from existing batch predictions without a second training-set forward pass; because it includes dropout and predictions occur before each optimizer update, it is a directional diagnostic, not an eval-mode train score. Compare it with validation MAE and primary train objective over epochs. Train-only mean and median constants must be fitted on train labels and applied unchanged to validation/test. The scored partition's own mean is only the mathematical R² reference. Report best epoch, runtime, peak memory, data/cohort/train fingerprints, race coverage, and all unchanged acceptance gates. Treat one combined run as a package comparison; it cannot assign causality to individual changes.

If this candidate remains weak, the next low-cost model diagnostic is a no-graph temporal/own-history predictor or boosted-tree baseline on the same prepared split. If that performs as well as the edge model, interactions add little under the current features. If it is poor too and training error is high, inspect target scale, feature distributions, masking and optimization; only then consider controlled capacity/LR changes. GCN is a simpler normalized-neighbor baseline but may smooth this small, directed, time-varying graph. PNA is a later option if degree and aggregation statistics demonstrably matter. PairNorm is only a candidate after measured embedding collapse. Do not add self-supervised losses, uncertainty heads, sample reweighting or new physics thresholds without a separate validation protocol.
