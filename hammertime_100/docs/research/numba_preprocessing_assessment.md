# Numba assessment for GNNv2 preprocessing

## Decision

Do not add Numba to the runner yet. The repository lock and active environment do not contain it. A temporary Numba 0.68 overlay was used for a full-wrapper synthetic benchmark, but its measured gain on packed fixtures was only about 4.5 microseconds per frame and it was slower on the evenly spaced case. That result is fixture-specific and too small and density-sensitive to justify adding a compiler dependency to the RAM-constrained preprocessing path without an authentic Windows profile.

No authentic `race_cache`/Parquet inputs or Windows run logs were present in this worktree. The Windows report is still verbal. This assessment therefore makes no claim about race-data speedup, total preprocessing time, or CPU utilization.

## Candidate code paths

| Path | Current work | Numba fit |
| --- | --- | --- |
| `physical_graph.build_physical_circuit_edges` | Converts per-frame driver mappings to eligible cars, sorts by circular distance, evaluates adjacent-car gap/speed/RBF/occlusion rules, then creates Torch tensors. Sorting is O(N log N) and the adjacent-car loop is O(N), over at most the small on-track field (about 20 cars); Python mapping access, sorting and Torch object creation surround it. See `hammertime_100/src/physical_graph.py:97-151`. | The only plausible scalar-kernel candidate. A useful experiment must include array preparation, compiled call and output/Torch construction. A per-frame kernel over tiny arrays could lose its arithmetic gain to these costs. Preserve stable tie order, float64 intermediates, thresholds, edge ordering, and masks if ever prototyped. |
| `preprocess.compute_time_gaps` | Pandas groups by race/time and copies each timestamp group before handling driver data. See `hammertime_100/src/preprocess.py:227-240`. The per-frame driver count is small; grouping, filtering, copying and object conversion are outside `njit`. | Low-priority kernel candidate. Profile pandas/group overhead first; do not expect JIT on the inner loop to remove it. |
| `context_features.prepare_context_features` | Trajectory history is already prepared by pandas stable sort/groupby shifts and the geometry arithmetic is vectorized NumPy over arrays. See `hammertime_100/src/context_features.py:235-289`. | No clear scalar Python kernel remains here. Numba would duplicate existing NumPy work and retain pandas grouping. |
| Context calibration | Membership selection, filtering, concatenation, deduplication and median-by-group use pandas operations (`context_features.py`, `fit_context_calibration`). | Not a suitable `njit` target without replacing the table/group semantics; no evidence supports that rewrite. |

The GNNv2 project dependency list currently has NumPy but not Numba (`pyproject.toml:6-23`; no Numba package entry in `uv.lock`). A Numba import in the data pipeline would add startup/import and compilation/cache behavior to every clean installation. `parallel=True` is not recommended for the current RAM-constrained Windows report: worker-local arrays and runtime overhead need measurement, and the user observed near-full system RAM.

## Fixture benchmark

- The reproducible, clearly synthetic script is `hammertime_100/tools/benchmarks/numba_physical_graph_microbenchmark.py`. Run it from the repository root with `uv run --frozen --no-sync --with numba==0.68.0 python hammertime_100/tools/benchmarks/numba_physical_graph_microbenchmark.py`. `--frames 5 --repeats 1` is a quick smoke command; defaults are 1,000 generated frames plus six deterministic contract cases and 50 timing passes per density scenario.
- A temporary non-locking uv overlay installed Numba 0.68.0 and NumPy 2.5.3. The locked project environment remained unchanged. The run used the current `physical_graph.py` implementation and a Numba prototype that includes mapping extraction, sorting, float64 array conversion, compiled kernel, and Torch output construction. It does not time just the numeric kernel.
- Both fixture scenarios had 20 eligible cars on ordinary generated frames. The packed fixture generated 14,105 edges across 1,006 frames; the evenly spaced fixture generated 106, with zero edges on its first ordinary frame. Six deterministic cases add circular wrap, equal-distance ties, the 2-second cutoff, the physical-v2 35 m/0.6 s corridor mask, invalid/missing/inactive/zero-speed rows, and a valid-flag row with NaN speed. The current builder filters the nonfinite speed before the kernel, so the prototype's max-speed-floor expression receives only finite values.
- Exact output parity (`torch.equal` for edge indices and float32 edge attrs, plus exact coverage and blocked counts) was checked against the existing builder on every frame in both scenarios.
- The benchmark runs on Python 3.12.14, Linux x86_64 (CachyOS kernel 7.3.0), Intel Core i5-13420H; it does not model the user's Windows CPU or memory. Timings summarize 50 repetitions over the same fixture frames, after correctness checking and JIT compilation. The archived run's packed current-builder median was 21.13 ms and the warm Numba wrapper was 16.59 ms (roughly 4.5 microseconds saved per fixture frame); the ratio of medians was 0.785. Evenly spaced current-builder median was 11.99 ms versus 13.20 ms for Numba (roughly 1.2 microseconds slower per fixture frame); the ratio of medians was 1.100. Repeated local runs varied, as expected for such short timings. First Numba call in a fresh process, including compilation and one candidate call but excluding Python/Numba imports, was 0.552 s. The prototype uses `cache=False`, `fastmath=False`, and no parallel execution. Numba compilation memory/RSS was not measured.
- No authentic `race_cache`/Parquet inputs or Windows run logs were present in this worktree, so there was no authentic-input profiling opportunity. The Windows report remains verbal. These microbenchmarks do not establish race-data speedup, full preprocessing time, CPU utilization, or process memory impact.
- No runtime source, project dependency, or lock file was changed. No project test suite or training was run for this assessment; the benchmark’s all-frame parity checks and quick CLI smoke run passed. Raw output is archived in ignored `.local/research-history/numba_physical_graph_fixture_2026-11-03.txt`.

## Runtime fit and limits

- Current official Numba docs state that nopython compilation is the route to native-loop performance and that object mode is slower; they recommend profiling actual code. The tested compatibility table lists Numba 0.68 with Python 3.10 through <3.16 and NumPy 1.22–<1.27 or 2.0–<2.6. This includes the locked project environment, but does not establish Windows run performance. See [performance tips](https://numba.readthedocs.io/en/stable/user/performance-tips.html), [installation and tested versions](https://numba.readthedocs.io/en/latest/user/installing.html), and [JIT/cache behavior](https://numba.readthedocs.io/en/stable/reference/jit-compilation.html).
- The first packed fixture suggests a possible speedup only when there are many accepted edges, while the sparse case is slower. The full-wrapper absolute difference was only a few milliseconds per 1,005 frames. That is not evidence that Numba would materially reduce the user's reported multi-hour pipeline, which includes alignment, table grouping, IO, graph objects, and memory pressure.
- `parallel=True` is not recommended for the current RAM-constrained Windows report. Per-worker memory and runtime overhead were not measured.

## Follow-up experiment before adopting Numba

On the Windows runner, collect a representative complete-race profile first: elapsed time and CPU time for alignment, gaps, context features, graph construction and coverage; process-tree RSS/commit and hard faults; and the exact commit, config, source cache fingerprint, race/frame counts and stride. Reconsider Numba only if physical-edge arithmetic is a material measured cost. Any follow-up must include conversion, sorting, JIT cold start, warm-cache runs and tensor construction on authentic captured frames, with exact edge index/order, float32 attrs, coverage, blocked counts, NaN handling, equal-distance ties and physical-v2 masks checked. Keep `fastmath=False`; avoid parallelization in the first prototype. Only add a pinned dependency and lock update if full-pipeline gains are material and the 16 GB host memory impact is acceptable.
