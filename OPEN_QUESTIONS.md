# Open questions from the overnight audit

Recorded 2026-10-30 (Asia/Kolkata). These require scientific or product decisions; the audit does not tune around them.

1. **DRS threshold discrepancy:** `hammertime_100/configs/default.yaml` specifies minimum lap loss **0.10 s** whereas `claude.md`, `claude_arc.md`, the evaluator's function default, and existing physics tests describe **0.40 s**. The existing configuration and thresholds are preserved. Which criterion is authoritative for future experiments?
2. **Clean-air label calibration:** target references currently use observed clean sectors from the entire session before temporal splitting, including future held-out observations. Documentation explicitly calls this session-specific label calibration, separate from train-only feature scaling. Is the intended result retrospective session calibration or prospective forecasting with a reference fitted on a separate calibration/training period? A change would alter label/split semantics and needs reviewer direction. Do not claim strict prospective holdout independence under the present contract.
3. **Existing artifacts:** the checked-in checkpoint, training history, images, and frontend JSON lack verified provenance under the audited pipeline. Preserve them as historical files; rerun with authentic data before treating them as current evidence.
4. **Physical car ahead versus classification:** `compute_time_gaps` uses race running order. A lapped car physically in front can differ from the next car in classification. Which proximity definition should govern wake edges and blue-flag interference? The audit does not change this scientific definition.
5. **Distance accuracy:** FastF1 multi-lap `Distance` is integrated from the telemetry slice origin. Anchoring at each observed lap start removes its cumulative offset but does not prove each integrated lap equals the configured physical circuit length. Review measured coverage and circuit-length calibration before interpreting missing last sectors or DRS completeness.
6. **Legacy frontend:** `frontend/app.js` contains invented default scores (58–69, labeled production), fallback rosters (107–130), sine gap history (1421–1433), random sector delays (1452–1454), score substitutions (1486–1488), and sample cards (1585–1590). `frontend/index.html` contains static passing assertions (23, 386, 443, 456, 514, 604), and `frontend/data/demo_data.py` synthesizes fallback metrics (124–177). These files are preserved as historical demonstration code, not verified research results. The exporter was not executed. Replacing that entire demonstration application requires a separately scoped data-integration review; use the artifact-backed Streamlit dashboard for audited results.
7. **Custom evaluation samplers:** `predict_test_set` attaches row metadata in `dataset.samples` order. M5's sequential test loader satisfies this requirement; shuffled or custom evaluation samplers are not supported without an explicit sample-index contract.
8. **Gate summary interpretation:** `run_pipeline.py` combines module/physics/presentation gates in `all_passed`, while MAE/R² acceptance flags are separate under `metrics`. Should a later reviewed change incorporate those existing flags into the aggregate? Until then, inspect both. This audit did not change thresholds or gate aggregation.
9. **Session aliases:** exact configured year/gp/type duplicates are rejected, including case differences. Different names for the same real event (for example, circuit versus event names) would require canonical FastF1 identity to detect reliably; verify session provenance before claiming race-held-out independence.
